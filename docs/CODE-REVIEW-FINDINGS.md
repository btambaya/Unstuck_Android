### [ ] Cold-launch notification deep link to a task/focus is lost (race with Room hydration) **[BLOCKER]**
- **where:** `/Users/ahmadtambaya/Desktop/projects/unstuck_android/app/src/main/kotlin/tech/csalliance/unstuck/ui/MainScaffold.kt:96`  ·  _and-vm_
- **what:** On a COLD launch from a notification, MainActivity.onCreate sets graph.pendingDeepLink before setContent, so the deep link value is present at MainScaffold's first composition. The LaunchedEffect(deepLink) block resolves the target by looking it up in `tasks` (collectAsStateWithLifecycle off store.tasks(), started WhileSubscribed at emptyList()). On cold start Room has not emitted yet, so `tasks` is still empty. For `unstuck://task/{id}` (line 110-114) the `if (tasks.any { it.id == id }) push(...)` is false → it only does `tab="today"; stack.clear()` and never opens the task. For `unstuck://focus/{id}` (line 103-108) `tasks.firstOrNull{...}` is null → it falls through to the today fallback and never starts focus. The effect is keyed ONLY on `deepLink`, and it immediately calls vm.consumeDeepLink() (line 117) setting it to null — so when `tasks` finally populates the effect does NOT re-run. Net: tapping a task reminder, a 'starts now' Start action, or any task-targeted push on a cold app reliably dumps the user on Today instead of the intended task/focus screen. This is the single most common notification path at launch.
- **fix:** In MainScaffold.kt, defer consumption until the data needed to route exists, and re-run the effect when tasks populates. Concretely: key the effect on both deepLink and tasks (`LaunchedEffect(deepLink, tasks)`), and in the task/focus/capture branches, when the target id is not found AND tasks.isEmpty(), `return@LaunchedEffect` WITHOUT calling consumeDeepLink() so it re-runs on the next Room emission. For the task branch specifically, do not run `tab="today"; stack.clear()` before the lookup succeeds. Only call vm.consumeDeepLink() once a route was actually taken (or the id is genuinely absent in a non-empty list). Equivalent alternative: await readiness before resolving, e.g. `vm.tasks.first { it.isNotEmpty() }` (kotlinx.coroutines.flow.first is already imported in AppViewModel) with a short timeout fallback to the Today route, then consume.

### [ ] Boot reschedule never runs — ReminderReceiver is exported=false but listens for BOOT_COMPLETED **[BLOCKER]**
- **where:** `/Users/ahmadtambaya/Desktop/projects/unstuck_android/app/src/main/AndroidManifest.xml:58-64`  ·  _and-notif_
- **what:** ReminderReceiver is declared android:exported="false" (line 60) yet registers an intent-filter for android.intent.action.BOOT_COMPLETED (line 62). BOOT_COMPLETED is broadcast by the system process (a different UID), so Android will NOT deliver it to a non-exported manifest receiver — the receiver must be exported for cross-app/system broadcasts. The entire ReminderScheduler.reschedule(app) call in ReminderReceiver.onReceive (ReminderReceiver.kt:21-23) is therefore dead on real devices. The scheduler's own KDoc promises alarms are "rescheduled on boot" (ReminderScheduler.kt:19), and exact alarms are cleared by the OS on reboot. Result: after every phone restart, ALL pre-task reminders (A1), starts-now (A2), and drift (A4) alarms are silently lost until the user happens to reopen the app (which re-arms via ReminderScheduler.observe in UnstuckApp.onCreate). For a punctuality/ADHD-support product whose core value is the reminder firing, this defeats the feature for anyone who reboots and doesn't reopen the app before the scheduled time.
- **fix:** In /Users/ahmadtambaya/Desktop/projects/unstuck_android/app/src/main/AndroidManifest.xml, change the ReminderReceiver to android:exported="true" (line 60), since it must receive the system BOOT_COMPLETED broadcast:

<receiver
    android:name=".surface.ReminderReceiver"
    android:exported="true">
    <intent-filter>
        <action android:name="android.intent.action.BOOT_COMPLETED" />
        <action android:name="android.intent.action.MY_PACKAGE_REPLACED" />
        <action android:name="android.intent.action.LOCKED_BOOT_COMPLETED" />
    </intent-filter>
</receiver>

Notes: (1) Adding MY_PACKAGE_REPLACED also re-arms alarms after an app update (which likewise clears alarms). (2) Optional hardening: split boot handling into its own dedicated exported receiver and keep the alarm-fire receiver non-exported, since the alarm PendingIntents are explicit (set component to ReminderReceiver) and don't need export — but the boot receiver does. (3) Verify on a physical Android 12+ device: schedule a reminder, reboot, and confirm it still fires without reopening the app.

### [ ] Shade-action writes (Resume/End/Reschedule) fire-and-forget on a process scope without goAsync()
- **where:** `/Users/ahmadtambaya/Desktop/projects/unstuck_android/app/src/main/kotlin/tech/csalliance/unstuck/surface/NotificationActionReceiver.kt:25-55`  ·  _and-notif_
- **what:** NotificationActionReceiver.onReceive handles ACTION_RESUME, ACTION_END, and ACTION_RESCHEDULE by calling FocusCommands.resume/end and ScheduleCommands.rescheduleToNextSlot, each of which does `app.graph.scope.launch { ... }` (FocusCommands.kt:46-48, ScheduleCommands.kt:20) and returns immediately. onReceive does NOT call goAsync(), so the moment it returns the receiver loses its foreground-receiver priority and the process becomes immediately killable. These handlers perform Room writes (setLiveSession, upsertSession, upsertTask, upsertCalBlock) and even network calls (notifications.sessionRecap, coordinator.write). If the process is cold/low-priority when the user taps the action from the shade — common for the paused check-in, which fires ~14 min after pausing, and for the reschedule action on a long-idle device — the launched coroutine can be truncated before the write commits, leaving the live session/session record in an inconsistent state (e.g. 'End' tapped but the session never ends, paused timer keeps nagging). Note ReminderReceiver does this correctly with goAsync()+pending.finish() (ReminderReceiver.kt:46-55), so the pattern is known; the action receiver just omits it.
- **fix:** In NotificationActionReceiver.onReceive, for the write-performing actions (ACTION_RESUME, ACTION_END, ACTION_RESCHEDULE), capture a PendingResult via goAsync() and keep the receiver alive until the async work commits, mirroring ReminderReceiver.kt:46-55. Concretely: change FocusCommands.resume/end and ScheduleCommands.rescheduleToNextSlot to accept an optional onComplete callback (or a PendingResult) and invoke pending.finish() in a finally block after their app.graph.scope.launch coroutine completes; in onReceive, call `val pending = goAsync()` before dispatching and pass it through so finish() runs when the write is done. Keep total work under the ~10s broadcast limit (these writes are quick). Alternatively, route these mutations through a short expedited WorkManager OneTimeWorkRequest (like PausedCheckinWorker) so they survive process death entirely. Do NOT add goAsync() to the non-write actions (ACTION_SNOOZE, ACTION_CAPTURE) since they only cancel/start an Activity.

### [ ] Room DB ships with version=1 + fallbackToDestructiveMigration() — first schema change silently destroys unsynced data
- **where:** `data/src/main/kotlin/tech/csalliance/unstuck/data/db/UnstuckDatabase.kt:8-23`  ·  _and-data_
- **what:** The database is declared @Database(version = 1, exportSchema = false) and built with .fallbackToDestructiveMigration() (line 21). The app is already shipped to testers at versionCode 22 / versionName 0.4.9. The JSON-blob records design means most domain changes need NO schema change (good), but the moment any structural change IS needed (a new @Entity, a new column on `outbox`, an index, etc.) Room will see version 1 -> 2 with no Migration registered and DESTROY the entire local database. Critically, that wipes the `outbox` table — pending offline writes (tasks created, sessions logged, captures) that have NOT yet reached Supabase. Those are unrecoverable: they exist only on-device until the OutboxFlusher drains them. `exportSchema = false` also means there is no schema JSON to diff/test migrations against, so the destructive path can ship unnoticed. This is a latent data-loss bomb that detonates on the first schema bump.
- **fix:** In data/src/main/kotlin/tech/csalliance/unstuck/data/db/UnstuckDatabase.kt: (1) Change line 11 to exportSchema = true and add `ksp { arg("room.schemaLocation", "$projectDir/schemas") }` in the :data build.gradle.kts, committing the generated schema JSON so CI can diff/test migrations. (2) Replace the blanket .fallbackToDestructiveMigration() on line 21. For non-schema releases no migration is needed; for any schema bump register explicit Migration objects via .addMigrations(...). If a reset is ever truly required, scope it with .fallbackToDestructiveMigrationFrom(...) excluding any version that may hold unsynced outbox rows — never a blanket destructive fallback. (3) Before bumping the version, add a MigrationTestHelper test asserting the `outbox` and `live_session` tables survive 1 -> 2, and/or force an OutboxFlusher.flush on next launch before applying any destructive path. The invariant: the `outbox` table must never be dropped while it holds rows, because (per OutboxFlusher.kt:30) ops are removed only after a successful server flush, so unflushed rows are the only copy of offline writes.

### [ ] Cross-account push leak: device FCM token is never unregistered on sign-out, so the previous user's morning brief is delivered to whoever is signed in now
- **where:** `app/src/main/kotlin/tech/csalliance/unstuck/sync/SyncCoordinator.kt:220-224`  ·  _and-critic_
- **what:** On sign-out, handle(NotAuthenticated) tears down realtime and calls store.clearAll(), but never deletes the device_tokens row on the server. The server table is keyed (user_id, device_id) with NO unique constraint on fcm_token (supabase/migrations/014_push_device_tokens.sql:24 — only `unique (user_id, device_id)`). So after User A signs out and User B signs in on the same physical device, MainActivity.kt:43-49 re-registers the SAME FCM token under (userB, device_id) while User A's row (userA, device_id, fcm_token=X) still exists. The morning-brief-dispatch cron iterates every user; when it processes User A it queries device_tokens by user_id and pushes User A's top task NAMES to fcm_token=X (send-morning-brief/index.ts:79-109), which is now physically User B's device. - **fix:** Two complementary fixes:

1. Unregister this device's token on sign-out (client). 2. Enforce single-owner per token (server, defense-in-depth). In register-push-token/index.ts, before the upsert, run `delete from device_tokens where fcm_token = :fcmToken and user_id <> :uid` so a given FCM token can only ever belong to one account. This guarantees correctness even if the client-side unregister fails (offline sign-out, crash) — the next account that registers reclaims the token and orphans the stale row. Optionally add a partial unique index on fcm_token (where fcm_token is not null) and upsert-on-conflict-fcm_token, but the pre-delete is simpler given the existing user_id,device_id conflict key.

### [ ] Realtime onEach has no per-event guard — one un-decodable row permanently kills that table's live mirror
- **where:** `sync/src/main/kotlin/tech/csalliance/unstuck/sync/RealtimeMirror.kt:79`  ·  _and-sync_
- **what:** Each table's realtime stream runs `flow.onEach { ... onUpsert(action.record) ... }.launchIn(scope)` (lines 79-86) with no try/catch around the decode. onUpsert calls DbRowCodec.decodeX, whose row DTOs require non-null fields (e.g. CalBlockRow.taskName, TaskRow.createdAt/updatedAt, enum kind). If a single realtime payload fails to decode (a future column/enum value, a partial UPDATE record, a null in a required field), the exception propagates out of onEach and terminates that flow's collection. The job lives under a SupervisorJob (AppGraph.kt:21) so siblings survive, but THAT table's mirror is dead for the rest of the app session with no resubscribe and only a swallowed log. The iOS port deliberately uses `try? change.decodeRecord(...)` per event (RealtimeMirror.swift:78-90) so a bad event is skipped and the stream keeps running — Android regressed this. Result: silent loss of cross-device live updates for, e.g., tasks until app restart.
- **fix:** In RealtimeMirror.subscribe, guard each event so one bad payload can never tear down the collection. Wrap the per-event body in runCatching and log+continue, mirroring iOS's `try?` per event. Replace lines 79-86 with: `val job = flow.onEach { action -> runCatching { when (action) { is PostgresAction.Insert -> onUpsert(action.record); is PostgresAction.Update -> onUpsert(action.record); is PostgresAction.Delete -> action.oldRecord["id"]?.let { onDelete(it.jsonPrimitive.content) }; else -> {} } }.onFailure { println(\"[realtime] $tableName event decode/apply failed: $it\") } }.launchIn(scope)`. As defense-in-depth, also add `.catch { e -> println(\"[realtime] $tableName stream error: $e\") }` before `.launchIn(scope)` so any non-decode flow error (e.g. a connection-level throwable) logs instead of silently killing the table's mirror.

### [ ] Outbox has no retry cap or dead-lettering — a permanently-failing op blocks its dependents forever
- **where:** `sync/src/main/kotlin/tech/csalliance/unstuck/sync/OutboxFlusher.kt:17-34`  ·  _and-data_
- **what:** OutboxFlusher.flush has no per-op attempt counter and no dead-letter path (grep for attempt/retry/maxAttempt across sync+data confirms none; OutboxEntity has no attempts column). If an op fails permanently — e.g. a payload the server rejects (constraint/RLS/validation 4xx), not just a transient network error — it is retried on every reconnect/sign-in indefinitely. The loop only makes progress on OTHER ops, so a poison-pill upsert sits in the queue forever, growing the outbox and re-hitting the server each pass. Worse, because cal_block ops carry dependsOn = parent task id (WriteThrough.kt:43-44) and an op is held back while its dependsOn is still pending (OutboxFlusher.kt:23), a poison-pill TASK op permanently wedges every cal_block that depends on it — those blocks never reach the server even though the failure is unrelated to them. There is no visibility (only println, OutboxFlusher.kt:28) and no user signal that writes are permanently stuck.
- **fix:** Add an `attempts: Int = 0` column to OutboxEntity. In OutboxFlusher, increment attempts on each failure and, after N attempts (or on a definitively non-retryable error), move the op to a dead-letter/parked state instead of leaving it pending — so it stops re-hitting the server and stops wedging dependents. Distinguish error classes from the Supabase client: treat HTTP 4xx (RestException with 400/403/409/422) as non-retryable (park immediately), and 5xx/network/timeout as retryable (keep retrying with the attempt cap). When a dependsOn op is parked/dead-lettered, do not keep its dependents pending forever — either release them or park them too, so one poison-pill task op can't silently block all its cal_blocks. Finally, surface a sync-error signal (e.g. a SyncStatus.Error / count of parked ops exposed off SyncCoordinator) so the UI can warn the user their changes aren't syncing, instead of the current println-only path (OutboxFlusher.kt:28).
